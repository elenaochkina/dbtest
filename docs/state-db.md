# State db

The state db is a Postgres database that keeps the results of every workflow run: what was
run, how long each phase took, and what was measured. Grafana reads it to draw per-run and
per-repetition charts.

## Where it runs

| | |
|---|---|
| Container | `dbtest-state`, image `postgres:18`, started by the console's launcher |
| Port | a free host port, preferably `5433` |
| DSN | `postgres://postgres:test@localhost:5433/postgres` |
| Data | named volume `dbtest-state`, mounted at `/var/lib/postgresql` |
| Schema | created by `migrate` in `state/state.go` on every `state.Connect` |

The launcher reuses a running container, starts a stopped one, or creates one when it is
missing. The container keeps running after the console quits.

## Schema

```
runs ──┬── downtime_results    one row per repetition (recovery)
       ├── benchmark_results   one row per pgbench result
       ├── checkpoints         row count and stock sum at a named point
       └── fingerprints        table digest at a named point
```

Every child table has `run_id → runs(id) ON DELETE CASCADE`, so deleting a run deletes its
results.

### Keys: how a result finds its run

```sql
-- runs
id     UUID PRIMARY KEY DEFAULT gen_random_uuid()

-- downtime_results (and the other child tables)
run_id UUID NOT NULL REFERENCES runs(id) ON DELETE CASCADE
```

| Part | Meaning |
|---|---|
| `runs.id` | **primary key**: the run's own ID, unique and never empty |
| `DEFAULT gen_random_uuid()` | Postgres creates the UUID when the run is inserted |
| `run_id` | **foreign key**: a copy of the run's `id`, saying "this row belongs to that run" |
| `REFERENCES runs(id)` | Postgres rejects a `run_id` that has no matching run |
| `ON DELETE CASCADE` | deleting a run deletes its rows, so no orphans are left |

One run has many repetition rows (one-to-many):

```
runs                                  downtime_results
id = 8f2c…  (aurora, crash, 3 reps)  ◄── run_id = 8f2c…  repetition 1
                                     ◄── run_id = 8f2c…  repetition 2
                                     ◄── run_id = 8f2c…  repetition 3
```

How the ID travels:

1. The `StartRun` activity inserts a row into `runs`; Postgres generates `id` and `StartRun`
   returns it (`RETURNING id`).
2. The workflow keeps it as `runID`.
3. `SaveDowntimeResults` writes each repetition with `run_id = runID`; `EndRun` updates the run
   `WHERE id = runID`.

`runs.id` and `workflow_id` are two names for the same run: `id` is the database key that the
child tables point at, and `workflow_id` (`recovery-20261022-054804`) is Temporal's ID, kept so
a run can be found from the Temporal UI.

### `runs`: one row per workflow

| Group | Columns | Notes |
|---|---|---|
| identity | `id`, `workflow_id`, `scenario`, `seed`, `provider` | `workflow_id` is the Temporal ID, e.g. `recovery-20261022-054804` |
| config | `disruption`, `repetitions`, `instance_class`, `high_availability`, `vcpu`, `memory_mib`, `disk_gib`, `region`, `postgres_version` | empty for runs that don't use them (pgbench, Docker has no class or region) |
| timeline | `started_at`, `provision_started_at`, `provisioned_at`, `ready_at`, `deprovision_started_at`, `delete_requested_at`, `ended_at` | `NULL` when the run stopped before that point; `delete_requested_at` is when AWS accepted the delete, not when the database was gone |
| outcome | `passed` | `NULL` until `EndRun` |
| durations | `provision_seconds`, `ready_seconds` | generated by Postgres from the timeline |

The timeline of a recovery run:

```
started_at
  provision_started_at ── Provision ──► provisioned_at ── WaitForReady ──► ready_at
     └────────── provision_seconds ──────────┘     └──── ready_seconds ────┘
  … seed, probe, disruptions …
  deprovision_started_at ── Deprovision ──► delete_requested_at   (AWS deletes in the background)
ended_at
```

### Generated columns

```sql
provision_seconds FLOAT8 GENERATED ALWAYS AS (EXTRACT(EPOCH FROM provisioned_at - provision_started_at)) STORED
```

- `provisioned_at - provision_started_at` is an interval, e.g. 5 min 2 s.
- `EXTRACT(EPOCH FROM …)` turns it into seconds: 302.
- `GENERATED ALWAYS … STORED`: Postgres computes it on every write and stores it like a normal
  column. Go code writes only timestamps, so seconds and timestamps can't disagree. A missing
  timestamp gives `NULL`.

### `downtime_results`: one row per repetition

| Group | Columns |
|---|---|
| links | `id` (primary key), `run_id` (foreign key to `runs.id`) |
| labels | `provider`, `disruption` |
| what happened | `repetition`, `disrupted_at`, `usable_again_at` |
| measurements | `readable_downtime_ms`, `writable_downtime_ms`, `lost_commits` |
| probe | `probe_interval_ms`, `probe_failures`, `probe_errors` (JSONB: error kind → count) |
| | `created_at` |

The run's config and timings stay in `runs`; a chart that needs them joins on `run_id`.
`probe_interval_ms` is the resolution of the downtime figures: rows recorded at different
intervals are not comparable. `UNIQUE (run_id, repetition)` makes a retried insert a no-op.

### `benchmark_results`, `checkpoints`, `fingerprints`

| Table | One row per | Main columns |
|---|---|---|
| `benchmark_results` | pgbench result | `tps`, `latency_avg_ms`, `latency_stddev_ms`, `scale_factor`, `clients`, `duration_seconds` |
| `checkpoints` | named checkpoint | `name`, `row_count`, `stock_sum`, `captured_at` |
| `fingerprints` | named table digest | `name`, `table_name`, `digest`, `captured_at` |

## Who writes what

| Write | Code | Called by |
|---|---|---|
| new `runs` row | `state.StartRun` | `StartRun` activity, at the start of a workflow |
| `ended_at`, `passed` | `Run.End` | `EndRun` activity, deferred, after `Deprovision` |
| `downtime_results` rows | `state.SaveDowntimeResults` | `SaveDowntimeResults` activity, once per recovery run |
| `benchmark_results` row | `state.SaveBenchmarkResult` | `SaveResult` activity, pgbench workflow |
| `checkpoints`, `fingerprints` | `Run.Checkpoint`, `Run.SaveFingerprint` | correctness scenarios |

Planned (recovery-metrics, steps 2 and 3): `StartRun` writes the config columns, and
`EndRun` writes the timeline.

## Changing the schema

`migrate` runs `CREATE TABLE IF NOT EXISTS`, which creates missing tables but never changes an
existing one. The state db is disposable, so after a schema change recreate it instead of
writing `ALTER TABLE` steps:

1. Quit the console.
2. `docker rm -f dbtest-state`
3. `docker volume rm dbtest-state`
4. Start the console. The launcher creates a new container and `migrate` builds the schema.

This deletes every saved run.

## Example queries

Provision and ready time per run:

```sql
SELECT workflow_id, provider, instance_class, high_availability,
       provision_seconds, ready_seconds
FROM runs
WHERE disruption IS NOT NULL
ORDER BY started_at;
```

Writable downtime per repetition, with the run's config:

```sql
SELECT r.workflow_id, d.repetition, d.provider, d.disruption, r.instance_class, r.high_availability,
       d.writable_downtime_ms / 1000 AS writable_seconds, d.lost_commits
FROM downtime_results d
JOIN runs r ON r.id = d.run_id
ORDER BY d.disrupted_at;
```

Average downtime by provider and disruption:

```sql
SELECT d.provider, d.disruption, r.high_availability,
       count(*) AS repetitions,
       avg(d.writable_downtime_ms) / 1000 AS avg_writable_seconds,
       max(d.writable_downtime_ms) / 1000 AS max_writable_seconds,
       sum(d.lost_commits) AS lost_commits
FROM downtime_results d
JOIN runs r ON r.id = d.run_id
GROUP BY d.provider, d.disruption, r.high_availability;
```

AWS databases that were never deprovisioned:

```sql
SELECT workflow_id, provider, instance_class, ready_at
FROM runs
WHERE provider <> 'docker' AND provision_started_at IS NOT NULL AND delete_requested_at IS NULL;
```

Connect with `psql postgres://postgres:test@localhost:5433/postgres`.
